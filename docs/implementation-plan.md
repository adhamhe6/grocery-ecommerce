# Implementation Plan

Status legend used throughout the docs: **Implemented** = exists and is covered by an executed test;
**Planned** = designed but not yet built. Nothing is listed as implemented until it runs.

## 1. Product vision and users

**Orchard Row** is a premium online grocer. Its promise: *fresh products, honest information, convenient
shopping, transparent pricing, dependable fulfilment.*

| User | Needs |
|---|---|
| Shopper | Find groceries fast, understand how each item is sold (kg / pack / each), see unit prices, choose delivery or pickup, control substitutions, pay safely, track the order, reorder |
| Store owner / manager | Run catalog, prices, promotions, branches, slots, staff; see real sales, waste and stock-risk numbers |
| Inventory manager | Stock, batches, expiry (FEFO), wastage, adjustments, transfers |
| Purchasing manager | Suppliers, purchase orders, goods receiving with batch/expiry capture |
| Fulfilment staff | Picking list, weighing, substitutions, packing, handover |
| Support | Find customers/orders, resolve complaints, cancellations and refunds |
| Marketing | Promotions, coupons, banners, recipes, policies |

## 2. Brand concept

- **Name:** Orchard Row (original working name; **no trademark, domain or social-handle availability has been checked**).
- **Tagline:** *Fresh, honestly labelled.*
- **Palette:** orchard green `#1F3D2B`, leaf `#3F7D4E`, paper cream `#FBF7EF`, clay accent `#B8532F`, citrus `#E3A72F`, ink `#1B1F1C`. Text/background pairs verified ≥ 4.5:1.
- **Type:** Fraunces (display, warm serif) + Instrument Sans (UI), both self-hosted via npm.
- **Imagery:** original, consistently composed *illustrated* product tiles on warm paper with a soft shadow, generated by the repo
  (`scripts/generate_demo_images.py`). They are explicitly **demo imagery**: no stock photos are used, because their licences
  and permanence could not be verified. Real photography is uploaded through the dashboard (processed to responsive WebP).
- **Voice:** plain, specific, never superlative. No "healthy/organic/chemical-free" unless a product record carries a verified claim.
- **Editable without code:** `StoreSettings` (name, tagline, logo, colours used by the theme tokens, contact, currency, locale, opening
  hours, socials, delivery/refund copy) plus per-branch data. Social URLs are placeholders flagged `is_placeholder`.

## 3. Target architecture

```
Browser ──► Next.js 15 (App Router, SSR/ISR, TypeScript, Tailwind)
              │  same-origin proxy  /api/* , /media/*
              ▼
        Django 5.2 + DRF  ──► PostgreSQL 16 (source of truth)
              │   ▲
              │   └── Redis 7 (cache, rate limits, Celery broker)
              ▼
        Celery worker + beat (email, expiry/low-stock alerts, reservation expiry, report exports, slot generation)
```

Decisions and why:

| Decision | Reason |
|---|---|
| **Django + DRF** (kept from legacy) | Mature ORM, migrations, constraints, row-locking; business rules live in services behind a versioned API usable by web, POS or mobile later |
| **Modular monolith**, no microservices | One deploy unit; transactional consistency across cart → stock → order → payment is the hard requirement |
| **Next.js + TypeScript** | SSR/ISR for SEO-critical catalog pages, one design system shared by storefront and staff dashboard |
| **Session-cookie auth + CSRF**, Next proxies `/api` same-origin | HttpOnly cookies (no tokens in JS), simple revocation, no CORS surface |
| **PostgreSQL only** | CHECK/partial-unique constraints, `SELECT … FOR UPDATE`, `pg_trgm` + FTS for search — no Elasticsearch needed at this scale |
| **Redis** with graceful degradation | Cache + throttling + broker; the app still serves when Redis is down (cache misses, throttle fail-open for reads, tasks run inline in dev) |
| **Celery** | Non-blocking emails/exports; idempotent tasks |
| **Illustrated demo imagery** | See §2 |

## 5. Data model (summary — details in `docs/data-model.md`)

Money: `DecimalField(12,2)`. Quantities/weights: `DecimalField(12,3)`. No floats anywhere in pricing or stock.

Notable constraints (database level): unique `Product.sku` and `slug`; `price >= 0`; `qty_min > 0`, `qty_step > 0`, `qty_max >= qty_min`;
`StockLevel`: `on_hand >= 0`, `reserved >= 0`, `reserved <= on_hand` (the database itself refuses to oversell);
`Batch.remaining >= 0`; `DeliverySlot`: `booked <= capacity`; unique `PaymentEvent.provider_event_id`; unique
`Receipt` per PO + idempotency key; unique order number; `Review` unique per (product, customer).

## 6. Grocery business rules

**Selling units.** `SaleUnit` rows (each, kg, g, 100 g, L, mL, pack, box, bundle, dozen) carry a measure kind
(count / weight / volume) and a factor to the base unit (kg or L). A product has a sale unit, price per sale unit,
`qty_min`, `qty_step`, `qty_max`, and optionally a **net content** (e.g. 500 g) so unit prices (per kg / per L) are comparable.
Server validation rejects any quantity that is not `qty_min + k·qty_step`.

**Variable weight.** Allowed only for weight-unit products. Customer orders an *expected* weight; picker records an *actual* weight.
- Tolerance (`weight_tolerance_percent`, default 10 %) = max variation the picker may record without escalation.
- Card authorisation = estimated total + tolerance buffer on variable lines; **final charge = actual weight × snapshot unit price, capped at the authorised amount**.
- Above the cap or outside tolerance the picker cannot finalise: customer approval (or re-pick) is required. Under-weight is always cheaper for the customer but flagged when beyond tolerance.
- Order lines persist `ordered_qty`, `expected_weight`, `picked_qty`, `unit_price`, `line_total_estimated`, `line_total_final`. The customer sees both.

**Substitutions.** Order-level policy: *allow substitutes · contact me first · no substitutes (refund)*; optional per-line override.
A candidate must be active, in stock at the branch, same measure kind, same leaf category (or explicit mapping), dietary-tag superset of the original,
and allergen-set subset. Customer never pays more than the original line price (store absorbs the difference; configurable).
`NO_SUBSTITUTES` makes proposing a substitute an error (`SUBSTITUTION_NOT_ALLOWED`); `CONTACT_ME` requires explicit customer approval; every step is written to order history.

**Inventory strategy.** *Reserve at order placement → commit at picking → release on cancel/short.* Pending-payment reservations expire after 15 min (Celery beat).
Reservations on batch-tracked products allocate batches **FEFO**, skipping expired/blocked batches. Late payment after expiry re-attempts reservation, else voids the authorisation.

**Expiry.** Only products flagged `tracks_batches` need lots. Each batch has `best_before` or `use_by` (`expiry_kind`); `use_by` expiry hard-blocks sale at the date, best-before is a configurable
`sell_until_days_before` buffer. Jurisdiction rules are configuration, not code.

**Cancellation/returns.** Customer self-cancel until picking starts; afterwards support only. Fresh goods are not returnable; complaints
(damaged/incorrect/missing) within `complaint_window_hours` (default 24) are reviewed by support and may produce partial refunds.

## 7. Checkout and payment architecture

`POST /api/v1/checkout/` (requires `Idempotency-Key`) runs in one transaction: lock cart → re-price on server → validate address/zone/slot/opening cut-off →
lock stock rows (ordered by id) → reserve → atomically book the slot (`UPDATE … WHERE booked < capacity`) → redeem coupon → create order snapshots → create `Payment` →
commit. Only after the DB commit is the payment provider called. Orders start `PENDING_PAYMENT`; they become `CONFIRMED` **only** from a verified provider event (webhook) or,
for pay-on-delivery, immediately.

Providers implement `create_payment`, `capture`, `void`, `refund`, `verify_webhook`.
- **Demo sandbox adapter (default in dev/test, refuses to load when `DEBUG=False` unless `PAYMENTS_ALLOW_DEMO=true`)**: a hosted "demo payment" page lets the tester choose succeed / fail / cancel; the backend then
  sends a signed event to the *real* webhook endpoint, so signature verification, de-duplication and state transitions are exercised exactly as in production. It never presents itself as a real transaction.
- **Stripe adapter**: written against the official SDK (manual-capture PaymentIntents, signed webhooks). Verified only at the SDK boundary (signature verification with locally generated
  signatures; network calls stubbed) — **not verified against a live Stripe sandbox** because no credentials are available here.
- **Pay on delivery/pickup**: payment recorded `PENDING_COLLECTION`, staff mark collected.

Webhook handling: verify signature → insert `PaymentEvent` (unique provider event id → duplicate is a no-op) → apply transition under row lock → emit side effects once.
A frontend redirect is never treated as proof of payment.

## 8. Fulfilment

`CONFIRMED → PICKING → PACKING → READY_FOR_PICKUP | READY_FOR_DISPATCH → OUT_FOR_DELIVERY → COMPLETED`, plus `CANCELLED`, `PAYMENT_FAILED`. Transition table lives in code and DB history rows
(`from`, `to`, actor, note). Payment status is a separate field. Picking screen shows items, units, expected weight, policy, actual weight input, availability, notes, and substitution actions.

## 9. Admin permissions (backend-enforced)

Roles: `SUPER_ADMIN, ADMIN, STORE_MANAGER, INVENTORY_MANAGER, PURCHASING_MANAGER, FULFILMENT_STAFF, CUSTOMER_SUPPORT, MARKETING_MANAGER, CUSTOMER`.
A permission matrix maps role → capabilities (e.g. `orders.fulfil`, `inventory.adjust`, `catalog.write`). Branch-scoped roles see only assigned branches
(querysets filtered server-side). Every consequential action writes an `AuditLog` row.

## 10. Performance and caching

- Catalog list/detail via `select_related/prefetch_related` and DB-side annotations (no N+1; query-count tests).
- Search: weighted FTS + trigram, GIN indexes; `EXPLAIN ANALYZE` captured in `docs/performance.md`.
- Cache (Redis, short TTL, explicit invalidation): category tree (10 min), store settings (5 min), homepage collections (60 s), report aggregates (5 min). **Never cached:** cart, prices at checkout, stock, payment/order data.
- Frontend: server components for public pages, ISR (`revalidate` 30–60 s), `next/image`, route-level code splitting, no client bundle for static content.
- Targets (to be *measured*, not asserted): LCP ≤ 2.5 s, INP ≤ 200 ms, CLS ≤ 0.1.

## 11. Background processing

Celery tasks (all idempotent): order/notification emails, `release_expired_reservations` (1 min), `generate_delivery_slots` (daily), `expiry_and_low_stock_scan` (hourly), `export_report_csv`, `cleanup_idempotency_keys`.
Dev/test run tasks eagerly; failures are logged and never mutate business state half-way (each task = one transaction).

## 12. Testing strategy

- **Backend:** pytest + pytest-django against real PostgreSQL; unit tests for pricing, quantity/unit validation, coupons, state machines; integration tests via DRF client for checkout, webhooks, receiving; **threaded concurrency tests** for stock oversell and slot overbooking; permission matrix tests (cross-account, cross-branch).
- **Frontend:** Vitest + Testing Library for cart/quantity/checkout components; ESLint + `tsc`.
- **E2E:** Playwright (Chromium) for the six mandated workflows against a seeded stack.
- **CI:** GitHub Actions with Postgres + Redis services.

## 13. Deployment

Docker Compose: `frontend`, `backend`, `worker`, `beat`, `postgres`, `redis` with health checks and `depends_on: condition: service_healthy`.
Production needs: managed Postgres + Redis, object storage for media, TLS, real secret management, real payment credentials, SMTP provider — documented in `docs/deployment.md`.
